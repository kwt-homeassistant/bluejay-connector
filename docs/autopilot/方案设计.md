# 方案设计

## 当前状态证据

- 客户端：`custom_components/aito/api.py`
- coordinator：`custom_components/aito/coordinator.py`
- 实体契约：`custom_components/aito/devices.py`、`sensor.py`
- 当前分支：`codex/energy-history-foundation`
- 正式环境：AITO `0.3.0`，本地候选不自动部署。

## 方案概述

客户端低频调用 `GET /vdas/v1/report/day-trip-range`。纯 Python 解析层只接收已确认的数值字段并丢弃未知字段、真实标识符和未来可能出现的位置数据。coordinator 先刷新最近 7 日，再在后台按 30 天窗口补齐最近 365 日，并通过 Home Assistant 私有 Store 逐批持久化；实体数据只接收聚合摘要和回填进度。

## 契约变化

- 请求头：沿用 APIG `X-Vehicle-Id`。
- 查询：`startDate`、`endDate` 均为 `YYYY-MM-DD`，范围含首尾日期；常规刷新为最近 7 日，首次回填窗口最多 30 日。
- 日字段：`date`、`odo`、`trips`。
- 单程字段：`tripOdo`、`tripStartTime`、`tripTime`、`avgSpeed`、`maxSpeed`、`avgPowerConsum`、`avgFuelConsum`。
- 新实体：最近一次行程里程/开始时间/时长、今日行驶里程、最近 7 日行驶里程、行程报告更新时间、归档覆盖天数和回填进度。

## 状态与失败语义

- 刷新成功且无行程：今日和近 7 日为 `0`，最近一程为 `unknown`。
- 请求或结构失败：保留上次成功缓存及旧更新时间，不生成新 `0`。
- 刷新周期：最多每 30 分钟一次，独立于 30 秒动态状态轮询。
- 完整脱敏记录只存在 coordinator 内存和 Home Assistant 私有 `.storage`，不进入 attributes、Recorder、diagnostics 或日志。
- 每批成功后先保存再推进内存覆盖状态；保存失败不会把该窗口标记为完成，并在 30 分钟后重试。
- 覆盖区间记录已经成功查询的日期，不以“是否有行程”判断完成，因此空窗口也能推进回填。
- 合并以新窗口覆盖同一天旧数据；归档只保留以当前本地日期计算的最近 365 天。
- 多个车辆或常规刷新与后台回填并发时，通过串行持久化锁避免整份 Store 相互覆盖。

## 风险与缓解

- 未公开 API 漂移：严格结构校验、合成边界测试、失败保留旧缓存。
- 时区导致日期偏移：按 Home Assistant 配置时区解释 App 时间戳，实体时间输出 UTC aware datetime。
- 请求压力与风控：常规刷新限制为 7 日/30 分钟；首次归档约 13 个请求、每批间隔 1 秒，失败后暂停 30 分钟，不调用详情接口。
- 隐私泄露：公开 fixture 全部合成，模型和私有存储不保存 `tripId`、坐标或未知字段。

## 回滚与降级

- 回退 fork 提交即可移除历史行程功能。
- 正式 HA 未部署该候选，因此本轮回滚不涉及服务、账号或车辆。

## 仓库代号与可发现性

- 新名称：`kwt-homeassistant/bluejay-connector`。
- manifest 的 documentation 和 issue tracker 使用新地址；本地 `origin` 同步更新。
- GitHub Topics 清空，Custom Property `component_type=custom_integration` 保留。
- GitHub 的旧仓库 URL 可能继续重定向，公开 fork 页面仍显示上游 `xiasi0/aito`，公开代码搜索也能命中 AITO 名称和接口路径；改名只降低名称级搜索命中率。
- 回滚时可将仓库名称改回，但旧新 URL 的缓存和重定向不保证立即消失。
